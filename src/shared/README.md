# Основа UI

`old-front`, `new-back` і `new-back-2` — довідкові копії. Робочий код не імпортує їх; вони виключені з TypeScript, ESLint і форматування.

## Провайдери та сесія

Кореневий layout підключає `Providers`: TanStack Query, `AuthProvider` та Query Devtools лише в development. Конфігурація кешу — `query/create-query-client.ts`.

`useAuth()` повертає `status`, `manager`, `error`, `isRefreshing`, `refreshSession()` та `logout()`. Стани: `loading`, `anonymous`, `authenticated`, `forbidden`, `error`.

Перевірка сесії — один спільний query `/managers/me`. Ролі беруться з відповіді, JWT не декодується. Сесія перевіряється при фокусі, відновленні з'єднання та кожні п'ять хвилин у відкритій активній вкладці. Мережева помилка після успішного завантаження не видаляє профіль; первинна помилка показує можливість повторити перевірку або вийти.

Зміна токена створює новий QueryClient і демонтує попереднє дерево. Старі query та mutation cache очищаються через [QueryClient.clear](https://tanstack.com/query/latest/docs/framework/react/reference/QueryClient). Токен не входить у query keys. Підтримуються зміни через `setAccessToken`/`clearAccessToken` у цій вкладці та події `storage` з інших вкладок.

401 захищеного query/mutation завершує лише відповідну поточну сесію. 403 окремої операції не розлогінює менеджера; 403 від `/managers/me` означає відсутність доступу до CRM. Невдалий login не запускає глобальне завершення сесії.

Повторні спроби є лише для query при мережевих/5xx помилках, максимум дві. 4xx, некоректний JSON та скасування не повторюються. Мутації не повторюються й не відкладаються до відновлення мережі.

## Вхід та вихід

```tsx
const login = useLogin(returnTo)

await login.mutateAsync({ email, password })
// login.isPending, login.error — для майбутньої форми.

const { manager, logout } = useAuth()
```

Перед збереженням токена `useLogin` перевіряє менеджерський профіль. Застаріла або скасована спроба не відновить сесію після зміни вкладки/акаунта. Після входу допускається лише внутрішня адреса `/main` або `/main/...`. Параметр повернення передається у hook явно, наприклад значенням `next` із search params.

`logout()` видаляє токен і кеш; приватний guard переводить на `/auth`. Серверного logout/refresh у поточному бекові немає. Для нових мутацій передавайте AbortSignal, якщо їх треба скасовувати при демонтажі: очищення кешу не відкликає операцію, яку сервер уже отримав.

## Маршрути та доступ

- `/` — інтро зі старого фронта: через 3 секунди перехід на `/main`, якщо є токен, або `/auth`. Валідність токена для CRM перевіряє `AuthGuard`.
- `(private)/layout.tsx` обгортає приватні сторінки в `AuthGuard`.
- `(public)` призначений для інтро, входу та відновлення пароля. Сторінки доступні незалежно від авторизації, без автоматичного перенаправлення залогованих.
- `/auth` — форма входу; `/forgot-password` — запит коду; `/forgot-password/confirm` — код і новий пароль. Приватні сторінки мають спільні меню й хедер; `/main` показує dashboard з доступними модулями.
- `/unauthorized` та помилка перевірки сесії мають мінімальні службові стани.

`AuthGuard` не монтує приватний клієнтський контент до перевірки. Це клієнтська перевірка для сесії в localStorage. Server Components, Server Actions і Route Handlers виконуються окремо: не завантажуйте й не передавайте через них приватні дані, покладаючись на цей guard. Для серверної авторизації потрібна окрема серверна сесія; сам бек перевіряє права кожного API-запиту.

## Ролі

```tsx
const { hasRole, hasAnyRole, hasAllRoles } = useRoles()

<RoleGuard allowedRoles={['admin', 'manager']}>
    <ManagementSection />
</RoleGuard>

<RoleGuard allowedRoles={['writer']} fallback={null}>
    <SendMailButton />
</RoleGuard>
```

За замовчуванням RoleGuard показує відмову в доступі; `fallback={null}` приховує елемент. Перевірка відповідає бекові: достатньо однієї дозволеної ролі; `admin` не замінює автоматично `writer` чи `marketolog`. Порожній список ролей менеджера не дає доступу до секції з вимогами. `MANAGER_ROLES` містить вбудовані назви, але бек дозволяє створювати нові ролі.

## Нові запити

```ts
const keys = createEntityQueryKeys('users')

useQuery({
    queryKey: keys.list(filters),
    queryFn: ({ signal }) => usersApi.list(filters, { signal }),
})
```

Ключі списку й запису розділені: `['users', 'list', filters]` та `['users', 'detail', id]`. Після зміни власного профілю/ролей інвалідуйте також `sessionQueryKey` або викликайте `refreshSession()`.

Компоненти UI розміщуються в `src/components` зі своїми `*.module.scss`. Шрифт Inter, назва, опис і favicon перенесені зі старого фронта. Формат: 4 пробіли, один порожній рядок між блоками; `npm run format` застосовує правила.

## Форми авторизації та тема

`components/auth-components` містить `LoginForm`, `ForgotPasswordForm`, `ResetPasswordForm` і спільні `AuthShell`, `AuthFormHeader`, `AuthFormInput`, `AuthFormSubmit`. Сторінки лише підключають потрібну форму. Відправлення обробляється через `form.onSubmit`; кнопка не має дубльованого `onClick`. Валідація використовує HTML-обмеження з DTO нового бека та перевірку збігу паролів. Остаточну перевірку виконує бек.

Вхід передає `{ email, password }`, відновлення — `{ email }`, підтвердження скидання — `{ email, code, password }`. Новий пароль має 8–128 символів, код — 6 цифр. Поля мають пов'язані підписи й autocomplete; помилки та стан відправлення показуються у формі.

`theme/ThemeProvider.tsx` застосовує світлу/темну тему через `data-theme` і використовує вже завантажений профіль менеджера. `useTheme()` з `theme/theme.ts` зберігає вибір локально; підтримується також формат налаштування старого фронта. Тема профілю застосовується після входу та коли змінюється серверне значення. Перемикач на публічних формах змінює локальну тему, без запису в API.

Спільні SCSS-міксіни перенесені в `shared/styles`, потрібні логотипи та іконки — в `public`. CRM призначена лише для десктопів. Форми мають фіксовану ширину 380px; мобільну адаптацію не додаємо. Зі старого фронта переносимо лише те, що використовується в поточному завданні. Інтро зберігає білий фон старої версії; анімація вимикається при `prefers-reduced-motion`.

## Навігація CRM

`features/crm/catalog.ts` — єдине джерело розділів, адрес, назв, груп і доступів. `config/routes.ts` залишає адреси авторизації та сумісні допоміжні функції. AppShell підключає Sidebar, Header і RoleGuard; недоступна сторінка не монтує свій контент.

Ролі: `admin`, `manager`, `writer`, `marketolog`. Партнерський розділ видимий маркетологу, але API-операції мають окремі серверні обмеження. Деталі актуальної реалізації та обмежень: [CRM](../features/crm/README.md) і [README проєкту](../../README.md).

Тема хедера зберігається через `PATCH /managers/me`, оновлює спільний профіль і повертає попереднє значення при помилці. Публічний перемикач зберігає тему локально. Кольори всього нового UI задані в `styles/tokens.scss`; міксіни не дублюють палітру.
